快速开始里，一个 `@Controller` 方法变成了可访问的 HTTP 路由。
这背后最重要的不是某个 API，而是 Feat Cloud 的工作模型：开发时用注解表达意图，编译期生成普通 Java 代码，运行时加载这些生成结果。

理解这一点之后，后面的 Controller、Bean、Profile、MyBatis、MCP 和部署问题都会更容易判断。
![注解代码经编译期处理生成 CloudService 并注册到 Router 的示意图](./img/runtime_1.png)
## 从注解到 `CloudService`

当项目执行 `mvn compile` 时，`feat-cloud-starter` 中的注解处理器会读取 `@Controller`、`@Bean`、`@Autowired`、`@RequestMapping` 等注解，并生成 `CloudService` 实现类。

这些生成类承担几类工作：

- 创建 Controller 和 Bean 实例
- 为字段注入依赖
- 调用初始化方法
- 把 URL 路由注册到 `Router`
- 在应用关闭时释放资源

所以运行时并不需要重新理解一遍你的注解。  
它只要通过 `ServiceLoader` 找到这些生成类，然后按固定生命周期调用即可。

## 启动生命周期

Feat Cloud 启动时，`ApplicationContext` 会通过 `ServiceLoader` 加载生成的 `CloudService`，然后分阶段调用它们。每个阶段都会先处理完所有服务，再进入下一阶段：

1. `loadBean(...)`：创建类级 Bean，并注册到应用上下文
2. `loadMethodBean(...)`：调用工厂方法，创建并注册方法级 Bean
3. `autowired(...)`：按生成代码完成依赖注入
4. `postConstruct(...)`：执行 Bean 初始化逻辑
5. `router(...)`：注册 HTTP 路由

![](./img/runtime_2.png)

这个顺序解释了很多行为：为什么类级 Bean 要先创建，方法级 Bean 才能通过参数取得依赖；为什么依赖注入发生在初始化之前；也解释了为什么路由要等初始化完成后才注册。

### 应用关闭阶段

`destroy()` 不属于启动流程。应用关闭时，Feat Cloud 会调用各个 `CloudService` 的销毁方法，生成代码再执行对应 Bean 上的 `@PreDestroy` 方法，释放应用持有的资源。

因此，可以把整个生命周期理解为：启动时完成创建、装配、初始化和路由注册；关闭时执行资源清理。

## 这对开发方式意味着什么

编译期生成带来的好处很直接：

- 启动时少做扫描和反射
- 路由和装配逻辑更接近普通方法调用
- 更容易进入 Native Image 路线
- 配置错误更容易在构建阶段暴露

它也带来一个边界：当你修改 Controller、Bean 或 `feat.yml` 这类编译期输入后，需要重新编译。  
如果只重启已经打好的 jar，生成代码不会自动变化。

## 修改后为什么要重新构建

Controller、Bean、`feat.yml` 和 MCP 声明都是编译期输入。你改了这些内容之后，旧 jar 里的生成代码不会自动变化。

所以本地开发时，IDE 要真正触发 Maven 编译；部署前，也要重新执行构建命令：

```bash title="重新生成并打包"
mvn clean package
```

如果你遇到“代码明明改了，路由或配置却没变化”，第一反应应该是检查生成代码有没有更新，而不是只重启应用。
