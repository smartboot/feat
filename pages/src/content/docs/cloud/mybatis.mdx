在[构建第一个业务应用](/feat/building/first-business-application/)中，我们已经完成了任务管理 API。Controller 接收请求，Service 组织业务动作，任务暂时保存在 `ConcurrentHashMap` 中。

这个实现适合认识应用结构，却不适合真正保存业务数据：应用重启后数据会丢失，多实例之间也没有共享状态。

这一篇不再从头创建另一套 CRUD 应用。我们沿用前一篇的 `Task`、`TaskController` 和 `TaskService`，只替换数据存储部分：

```text
HTTP 请求
   ↓
TaskController       保持不变
   ↓
TaskService          从 Map 改为调用 Mapper
   ↓
TaskMapper           新增
   ↓
MyBatis
   ↓
数据库
```

完成后，原来的 HTTP 接口和 curl 命令仍然可以使用。变化集中在 Service 以下，这正是前一篇把业务逻辑与存储实现分开的意义。

## 添加依赖

请先完成前一篇的 Feat Cloud 项目。保留原有的 `feat-cloud` 运行期依赖和 `feat-cloud-starter` 编译期依赖，再增加 MyBatis 与数据库驱动。

下面沿用仓库 MyBatis 示例中的版本：

```xml title="pom.xml"
<dependency>
    <groupId>org.mybatis</groupId>
    <artifactId>mybatis</artifactId>
    <version>3.5.15</version>
</dependency>

<dependency>
    <groupId>com.h2database</groupId>
    <artifactId>h2</artifactId>
    <version>2.2.224</version>
</dependency>
```

这里使用 H2 内存数据库，是为了让示例不依赖外部数据库服务。它适合验证接入流程，不代表生产环境必须使用 H2。

## 配置 MyBatis

在项目的 `src/main/resources/feat.yaml` 中增加 MyBatis 配置：

```yaml title="feat.yaml"
feat:
  mybatis:
    path: mybatis/mybatis-config.xml
    initial-sql: mybatis/ddl/schema.sql
```

- `path` 指向 MyBatis 主配置文件。Feat Cloud AOT 会在编译期读取并解析它；修改配置路径或 XML 后，需要重新构建。
- `initial-sql` 指向应用启动时执行的初始化脚本。脚本内容在启动时从 classpath 读取；修改脚本内容后，需要确保新文件进入应用包并重新部署。

接着创建 `src/main/resources/mybatis/mybatis-config.xml`：

```xml title="mybatis-config.xml"
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE configuration
        PUBLIC "-//mybatis.org//DTD Config 3.0//EN"
        "https://mybatis.org/dtd/mybatis-3-config.dtd">
<configuration>
    <settings>
        <setting name="logImpl" value="STDOUT_LOGGING"/>
    </settings>
    <environments default="h2_mem">
        <environment id="h2_mem">
            <transactionManager type="JDBC"/>
            <dataSource type="POOLED">
                <property name="driver" value="org.h2.Driver"/>
                <property name="url" value="jdbc:h2:mem:feat-demo;DB_CLOSE_DELAY=-1"/>
                <property name="username" value="sa"/>
                <property name="password" value=""/>
            </dataSource>
        </environment>
    </environments>
    <mappers>
        <package name="com.example.tasks.mapper"/>
    </mappers>
</configuration>
```

这里有一个重要约束：当前 Feat Cloud AOT 对 MyBatis 数据源的重建只支持 MyBatis 的 `POOLED` 类型。使用 `UNPOOLED`、`JNDI` 或自定义 DataSource 时，不要假设可以直接沿用这条接入路径。

AOT 会根据 XML 重建 MyBatis 的 `Configuration`，并非把所有自定义配置原样保留。TypeHandler、typeAlias、ObjectFactory、带参数的插件等扩展配置，接入后都应单独验证。

## 创建数据表

创建 `src/main/resources/mybatis/ddl/schema.sql`：

```sql title="schema.sql"
CREATE TABLE IF NOT EXISTS task_info (
    id VARCHAR(64) PRIMARY KEY,
    title VARCHAR(255) NOT NULL,
    completed BOOLEAN NOT NULL DEFAULT FALSE
);
```

`initial-sql` 会在每次应用启动时执行，因此这里使用 `CREATE TABLE IF NOT EXISTS`，避免重复启动时删除已有数据。

生产环境不要把 `DROP TABLE` 等破坏性语句放进启动脚本。数据库结构升级应交给 Flyway、Liquibase 或团队已有的数据库迁移流程管理。

## 编写 Mapper

在 `src/main/java/com/example/tasks/mapper` 下创建 `TaskMapper.java`：

```java title="mapper/TaskMapper.java"
package com.example.tasks.mapper;

import com.example.tasks.model.Task;
import org.apache.ibatis.annotations.Delete;
import org.apache.ibatis.annotations.Insert;
import org.apache.ibatis.annotations.Mapper;
import org.apache.ibatis.annotations.Param;
import org.apache.ibatis.annotations.Select;
import org.apache.ibatis.annotations.Update;

import java.util.List;

@Mapper
public interface TaskMapper {

    @Select("SELECT id, title, completed FROM task_info ORDER BY id")
    List<Task> selectAll();

    @Select("SELECT id, title, completed FROM task_info WHERE id = #{id}")
    Task selectById(@Param("id") String id);

    @Insert("INSERT INTO task_info(id, title, completed) VALUES(#{id}, #{title}, #{completed})")
    int insert(Task task);

    @Update("UPDATE task_info SET title = #{title}, completed = #{completed} WHERE id = #{id}")
    int update(Task task);

    @Delete("DELETE FROM task_info WHERE id = #{id}")
    int deleteById(@Param("id") String id);
}
```

Mapper 仍然是标准 MyBatis 接口：用注解或 XML 描述 SQL，由 MyBatis 执行。Feat Cloud 不会替你改写 SQL，也不要求你换成另一套数据访问 API。

`@Mapper` 标记接口，`mybatis-config.xml` 中的 `<package>` 指定 Mapper 所在包。编译期生成的接入代码会把 Mapper 包装成 Feat Cloud 可以管理和注入的 Bean。

## 替换 Service 的存储实现

回到前一篇的 `TaskService`。删除原来的 `ConcurrentHashMap` 和 `AtomicLong`，改为注入 `TaskMapper`：

```java title="service/TaskService.java"
package com.example.tasks.service;

import com.example.tasks.mapper.TaskMapper;
import com.example.tasks.model.Task;
import tech.smartboot.feat.cloud.annotation.Autowired;
import tech.smartboot.feat.cloud.annotation.Bean;

import java.util.List;
import java.util.UUID;

@Bean
public class TaskService {

    @Autowired
    private TaskMapper taskMapper;

    public void setTaskMapper(TaskMapper taskMapper) {
        this.taskMapper = taskMapper;
    }

    public List<Task> findAll() {
        return taskMapper.selectAll();
    }

    public Task findById(String id) {
        return taskMapper.selectById(id);
    }

    public Task create(String title) {
        Task task = new Task(UUID.randomUUID().toString(), title, false);
        taskMapper.insert(task);
        return task;
    }

    public Task update(String id, String title, boolean completed) {
        Task current = taskMapper.selectById(id);
        if (current == null) {
            return null;
        }

        Task updated = new Task(id, title, completed);
        return taskMapper.update(updated) > 0 ? updated : null;
    }

    public boolean delete(String id) {
        return taskMapper.deleteById(id) > 0;
    }
}
```

这里继续使用前一篇的 `Task` 模型，因此不需要修改 `TaskController`。Controller 仍然调用 `findAll`、`findById`、`create`、`update` 和 `delete`，不需要知道底层已经从 Map 换成了数据库。

如果你希望把 UUID 换成数据库自增主键，需要同步调整实体类型、表结构和插入语句；这属于数据库设计选择，不是 Feat Cloud 接入 MyBatis 的要求。

## 重新编译并验证

Feat Cloud 会在编译期解析 MyBatis 配置、识别 Mapper，并生成相应的装配代码。首次接入或修改 Mapper、配置文件后，执行：

```bash
mvn clean compile
```

然后重新运行原来的 `Bootstrap.main()`。访问接口的方式与前一篇相同：

创建任务：

```bash
curl -i -X POST http://localhost:8080/tasks \
  -H 'Content-Type: application/json' \
  -d '{"title":"把内存存储替换成 MyBatis"}'
```

查询任务：

```bash
curl http://localhost:8080/tasks
```

更新和删除仍然使用原来的接口：

```bash
curl -i -X PUT http://localhost:8080/tasks/<task-id> \
  -H 'Content-Type: application/json' \
  -d '{"title":"已经接入 MyBatis","completed":true}'

curl -i -X DELETE http://localhost:8080/tasks/<task-id>
```

将 `<task-id>` 替换成创建接口返回的实际 ID。因为示例使用 H2 内存数据库，应用进程退出后数据库内容也会消失；如果要验证重启后的持久化，需要换成文件型或独立数据库，并配置对应驱动与连接信息。

## Mapper 的会话与事务边界

通过 `@Autowired` 注入的 Mapper 看起来像普通对象，但它是 Feat Cloud 编译期生成的包装类。当前实现中，每次 Mapper 方法调用都会独立执行一次 `openSession(true)`：打开会话、执行 SQL、自动提交并关闭。

这对单条 SQL 很方便，但它不等于一个业务方法自动拥有事务。

例如，一次业务操作需要先写任务表，再写操作记录表。如果两个 Mapper 方法分别使用各自的自动提交会话，第一条 SQL 可能已经提交，第二条失败时无法回滚第一条。

### 使用同一个 SqlSession

需要跨多条 SQL 保证原子性时，注入命名 Bean `sessionFactory`，在同一个手动提交的会话中获取 Mapper：

```java
import com.example.tasks.mapper.TaskMapper;
import com.example.tasks.model.Task;
import org.apache.ibatis.session.SqlSession;
import org.apache.ibatis.session.SqlSessionFactory;
import tech.smartboot.feat.cloud.annotation.Autowired;
import tech.smartboot.feat.cloud.annotation.Bean;

@Bean
public class TaskTransactionService {

    @Autowired
    private SqlSessionFactory sessionFactory;

    public void setSessionFactory(SqlSessionFactory sessionFactory) {
        this.sessionFactory = sessionFactory;
    }

    public void createAndUpdate(Task task) {
        try (SqlSession session = sessionFactory.openSession(false)) {
            TaskMapper mapper = session.getMapper(TaskMapper.class);
            mapper.insert(task);
            task.setCompleted(true);
            mapper.update(task);
            session.commit();
        }
    }
}
```

`false` 表示关闭自动提交。只有显式调用 `commit()` 才会提交这组操作；如果执行过程中抛出异常，关闭未提交的会话会结束这次事务。

注意：事务体内的所有数据库操作都必须使用 `session.getMapper(...) `得到的 Mapper。不要一部分使用这个 Mapper，另一部分又调用注入的自动提交 Mapper，否则它们不在同一个事务里。

### 把事务边界收敛成模板

如果多个业务方法都需要手动事务，可以把会话创建、提交和关闭集中起来：

```java
import org.apache.ibatis.session.SqlSession;
import org.apache.ibatis.session.SqlSessionFactory;
import tech.smartboot.feat.cloud.annotation.Autowired;
import tech.smartboot.feat.cloud.annotation.Bean;

import java.util.function.Function;

@Bean
public class TxTemplate {

    @Autowired
    private SqlSessionFactory sessionFactory;

    public void setSessionFactory(SqlSessionFactory sessionFactory) {
        this.sessionFactory = sessionFactory;
    }

    public <T> T execute(Function<SqlSession, T> work) {
        try (SqlSession session = sessionFactory.openSession(false)) {
            T result = work.apply(session);
            session.commit();
            return result;
        }
    }
}
```

业务代码通过传入的 `SqlSession` 获取 Mapper，并在同一会话内完成所有 SQL。模板没有自动传播事务：如果一个 Service 在事务回调之外调用另一个注入 Mapper 的 Service，后者仍会使用自己的自动提交会话。

也不要在事务回调内部捕获异常、打印后返回一个普通失败值。异常被吞掉后，模板无法知道业务操作失败，代码仍可能走到 `commit()`。需要转换业务错误时，应让异常穿出事务边界，再在更外层处理。

## 这一层的职责边界

接入 MyBatis 后，应用的职责划分仍然是：

- Controller 处理 HTTP 输入与输出。
- Service 组织业务动作，并决定事务边界。
- Mapper 描述 SQL。
- MyBatis 管理 SQL 执行和会话。
- Feat Cloud 在编译期生成 Mapper 接入与 Bean 装配代码。

Feat Cloud 不会替代 MyBatis 的数据访问职责，也不会自动为多个 Mapper 调用建立业务事务。把这条边界理解清楚，后续无论换数据库、引入迁移工具，还是增加缓存，都可以沿着已有的业务结构继续演进。
