# 路线图

这份文档回答一个问题：**feat-plus 要做成什么样的后台底座，以及为什么某些 RuoYi 有的东西我们不做。**

判断标准只有一条：这个能力能不能让一个真实团队「敢把 feat-plus 拿去接需求」。功能数量不是标准。

---

## 定位

不做 RuoYi 的复刻。RuoYi 已经占据了「Spring Boot 后台脚手架」这个生态位，功能、教程、代码生成生态都极其成熟，正面复刻必输。

feat-plus 的立足点是 Feat 的技术模型：

| | Spring Boot 系（RuoYi 等） | feat-plus |
|---|---|---|
| 装配时机 | 运行期反射扫描 | 编译期注解处理，生成 `FeatApplication` |
| 启动 | 秒级 | 毫秒级 |
| 内存 | 数百 MB | 数十 MB |
| 产物 | 需要 JVM + 大量反射元数据 | 可选 native image |
| 生成的代码 | 运行期魔法 | 人能读、能改、能 review 的 Java 源码 |

所以路线图围绕一件事展开：**把「后台系统必备的那部分」用编译期模型重新实现一遍**，而不是把 Spring 时代的运行期补丁搬过来。

---

## 2026 年的重估：为什么生成器不是重点

上一版路线图把「代码生成器」放在第三梯队，当作能正面赢 RuoYi 的差异点。这个判断要撤回。

生成器卖的是**「少写样板代码」**。而写样板代码恰好是 AI 最擅长、成本已经接近零的部分：复制一个列表页改字段、照着 Mapper 写一个 Service，今天都是几十秒的事。省下这两小时，换不来一个产品决策。

代价却是永久的：

1. **生成物必然被改。** 生成的 CRUD 只能覆盖「薄业务」，真实项目第二天就要加审核状态、加导入、加特殊校验。改完就再也回不去——再生成一次会丢掉所有改动。
2. **于是项目里长期并存两套范式。** 一套是生成的原样，一套是人改过的。AI 写代码靠模仿「周围多数派」，两套范式会让它随机挑一套，最后长出第三个变种。这是 AI 编程时代最贵的债务。
3. **RuoYi 的 gen 能活下来，是因为它的生成物业务太薄。** 那是脚手架的定位，不是企业项目的定位。

**结论：CRUD 代码生成器划入非目标。**

但有一件事不能跟着一起丢：**接口契约的机器可读化（OpenAPI）**。它不是生成器——它是把「编译期已经知道的全部路由、参数、返回类型」导出成一份 AI 能直接读的契约。人看文档，AI 读 spec。这条要从第三梯队提前，理由见下。

---

## AI 编程对架构的五条要求

「架构优秀」是个形容词，不可执行。换成五条能逐项对照的判据：

| # | 判据 | 为什么在 AI 编程下更重要 |
|---|---|---|
| 1 | **横切关注点必须是机制，不是约定** | 人写代码会记得「再调一下 require」，AI 不会。它会写出一个语法正确、逻辑正确、但漏了数据范围过滤的 Service，而且不报错。安全语义（鉴权、数据范围、软删、审计）必须由框架强制，漏接要编译失败或启动失败 |
| 2 | **错误要尽早暴露** | AI 写得快，人工 review 跟不上。能在编译期、启动期失败的东西，不要留到运行期静默失效——「主管看到了不该看的数据」这种 bug 没有报错，只有后果 |
| 3 | **单次改动的可读面要小** | AI 上下文有限。改一个功能要读 3 个文件是合理的，要读 30 个就不合理。这条决定模块边界按「变更原因」切，而不是按「技术层」切 |
| 4 | **同构性优先于灵活性** | 同类东西只允许一种写法。两个变种会生出第三个；三个变种之后 AI 每次都在猜 |
| 5 | **约束要可验证** | 每条约定都要有断言。AI 能自己跑断言，读不懂「请注意」。218 项回归断言在 AI 时代的价值比手写时代更高——它是让 AI 放手改的安全网 |

按这五条对照现在的 feat-plus，缺的东西很清楚：事务没有（判据 2 的反面）、数据权限靠人拼字符串（判据 1 的反面）、加一个字段要动八个文件（判据 3）、列表页 857 行且每页写法不一（判据 4）、错误码缺失只能字符串匹配（判据 5）。

下面的梯队按这个顺序重排。

## 第一梯队：把地基做成机制

这一层的共同点：**不做，后面写的每一行业务代码都是「演示级正确」。** 它们不产生新功能，只决定已有功能在真实数据下是否成立。

### 1. 事务边界（最高优先）

**不做 `@Transactional` 注解。** Feat 的装配在编译期完成，为一个注解在注解处理器里维护事务语义（传播行为、只读、回滚规则、内层回滚外层不复位），等于把 Spring 最重的那部分搬过来，与「一眼看得见」相反。

Feat 本身已经够用：`sessionFactory` 是命名 Bean，业务 Bean 直接注入即可——

```java
@Autowired
private SqlSessionFactory sessionFactory;

SqlSession session = sessionFactory.openSession(false);   // false = 手动提交
UserMapper mapper = session.getMapper(UserMapper.class);
```

不需要注解，不需要代理，不需要 ThreadLocal。注入之所以成立，是因为生成的装配分阶段：`loadBean` 阶段创建 Bean 并在末尾 `addBean("sessionFactory", ...)`，`autowired` 阶段才做注入，所以取得到。

问题不在于能不能写，而在于**漏写不会有任何提示**。下面三个坑必须写进规范：

1. **注入的 Mapper 与手开的 session 是两套。** `@Autowired UserMapper` 是生成代码包过的版本，每个方法 `openSession(true)` 独立提交。事务方法体里必须全部换成 `session.getMapper(...)`——混用一个，那一笔写就落在事务外，接口照常返回成功。
2. **跨 Service 不传播。** A 方法开了 session 调 B，B 里注入的 Mapper 自己开会话并提交。要么把 session 传下去，要么用模板把整段调用包住。
3. **必须 close。** 数据源是 MyBatis 的 `PooledDataSource`，漏 close 会耗尽连接池，表现是服务假死而不是报错。

所以目标形态是**一个显式事务模板**，不是每个方法手写 try / finally：

```java
txManager.execute(session -> {
    UserMapper mapper = session.getMapper(UserMapper.class);
    ...
    return saved;
});
```

边界显式、可读、可 grep，业务代码不碰 close 与 rollback；`ActivityRecorder` 这类「无论成败都要记」的旁路写，在模板里单独开会话即可（对应 REQUIRES_NEW）。这比注解更符合判据 1——不是靠「记得开事务」，而是靠一个只有一种入口的入口。

如果连模板也不引入，那就退化成纯约定：每个写方法自己开 session，靠 review 和断言兜底。代价要认：判据 1 说的「人能记住、AI 记不住」，在事务上会以「某次上线少提交一笔」的形式出现。

**文档欠账要一起还。** `mybatis.mdx` 通篇没有 `sessionFactory`、`SqlSession`、事务，只有一句「后面扩展权限、事务、校验时结构不会乱」；`demo/mybatis` 的 Service 又示范了 `catch (Exception e) { return false; }`——吞掉异常恰好让事务失去意义。补一节「会话与事务」是这件的必要部分。

### 2. 数据权限从「约定」变成「机制」

现在落地方式是：`SqlFragments` 手拼字符串 + 每个 Controller 手调 `accessGuard.require()` + 把 `AccessContext` 一路传到 Mapper。

已经翻过一次车——`ActivityController` 拿到 context 后又丢了，范围配置静默失效。第二次会发生在客户写的第二个业务模块上，而且不会有人发现。

这正是判据 1 说的那种「人能记住、AI 记不住」的东西。目标形态二选一：

- `@DataScope(deptColumn = "u.department_id", userColumn = "a.creator")` 标在 Mapper 方法上，AOT 期把过滤片段拼进 SQL；
- 或者把 `AccessContext` 变成 Mapper 方法的必填参数，漏传直接编译不过。

顺带解决权限点的三处维护（Java `Permission` / 前端 `types.ts` / 种子角色字符串）：Java 为唯一真相，前端从导出产物生成，启动时再校验一次种子数据里的 key，非法就 fail fast。

### 3. 数据库迁移与索引

`schema.sql` 全是 `CREATE TABLE IF NOT EXISTS`，**给客户已有的库加一列没有任何路径**——只能删库重来。这条不解决，feat-plus 永远只能做新项目，进不了任何存量系统。

最低成本方案：`db/migration/V1__*.sql` 按版本顺序执行 + `sys_schema_history` 记录已执行版本，与建表脚本共用一套。

同时补索引约定。现在 `CREATE INDEX` 一条都没有：`sys_user.department_id / status`、`sys_activity.creator / created_time / kind`、`sys_user_role.role_code` 上的查询全是全表扫。数据量一上来，「轻快」这个卖点会被自己毁掉。

### 4. 错误契约与可运维性

现在的问题：500 时把 `e.getMessage()` 原样返回前端（漏 SQL、漏类名）；只有中文 message 没有错误码，第三方集成只能字符串匹配；没有 `/health` `/ready`，容器编排没法配探针；没有 traceId，客诉来了查不到那一次请求。

四件事一起做，因为它们是同一件事的不同侧面——**让错误可被程序处理，而不是只被人读**：

- `DomainException` 加业务错误码，message 走资源文件（也为 i18n 留口）
- 500 只回通用话术 + traceId，全量留在日志
- `/health`、`/ready`（可以极简，但要有）
- 请求级 traceId 透传 + 访问日志（方法、路径、耗时、状态、操作人）

## 第二梯队：让 AI 改得对

第一梯队解决「写错会炸」，这一层解决「写起来要读太多、猜太多」。

### 5. 接口契约机器可读（OpenAPI 导出）

理由和上一版不同了。上一版说它是「编译期副产物，顺手的事」；现在它是**AI 的接口上下文**。

AOT 处理期手里已经有全部路由、方法、参数、返回类型。导出 `openapi.json` 之后：AI 不用读 12 个 Controller 才知道有哪些接口、参数叫什么、返回什么结构；前端 `types.ts` 也可以从它生成，不用手写 244 行再去和 Java DTO 逐字段对齐。

这条之所以不能跟着「生成器」一起砍掉：它生成的是**契约**，不是**实现**。契约变质了是真问题（前后端漂移），实现怎么写是 AI 的自由。

### 6. 模块边界重划（已完成 · 2026-11-01）

原来两套混着：外层按 feature（`user/` `role/`），里层按层（`controller/` `service/`），`common/` 是杂物间——`Permission`、`DataScope`、`SqlFragments`、`ApiController` 全塞一起，`SqlFragments` 里同时躺着用户和日志两个模块的 SQL。

现在统一按层：`controller / service / mapper / model / dto / security / token / common / seed`，共 76 个类。

三个判断写在 `README.md` 的「结构」一节：

- **`model` 与 `dto` 不合并**。`UserAccount` 有 `passwordHash` / `isDeleted`，`UserItemResponse` 没有；合并后密码哈希直接进 JSON，OpenAPI schema 也跟着错。
- **`SqlFragments` 跟 `mapper` 走**，不留在 `security`。否则 `mapper` 用它的常量、它又反过来引用 `mapper` 接口，两层成环。
- **部门子树算法抽到 `security/DepartmentTree`**（纯函数，入参是部门行）。原来放在 `DepartmentService`，导致 `security → service`，而 `service → security` 本来就存在，成环。

**约束变成机制**：`scripts/check_layers.py` 白名单校验 76 个类的 import，CI 第一步执行。三条硬规则——`controller` 不得直接用 `mapper`（绕过 Service 就等于绕过数据范围校验）、`security` 不得依赖 `service`/`controller`、`model` 不依赖本项目任何包。

**未完成**：框架层与业务层仍是同一个 module，`feat-plus-core` 独立发包还没做（见「分发形态」缺口）。

### 7. 前端同构抽象

`UserListPage.tsx` 单文件 857 行、14 个 `useState`、表单手写；`react-hook-form` 和 `zod` 装了但从未 import。每加一个列表页就得复制一遍再改。

不是为了少写代码——是为了**把「改一个列表页」的上下文从 857 行压到 120 行**。判据 3 和 4 都指向这里：`<DataTable columns>` + `useListQuery` + `<FormDialog schema>` 三件套，让同类页面只有一种写法。

### 8. 项目级 AGENTS.md

仓库根有 `AGENTS.md`，写的是「用 Feat 框架会踩的 12 个坑」；`demo/feat-plus` 自己没有。

AI 会读这个文件。把 feat-plus 的约定（软删五字段、权限点登记位置、数据范围必须怎么接、新增模块要动哪几个文件、断言在哪）写进去，比写在 README 里有效一个数量级——README 是给人看的，AGENTS.md 是给写代码的那个东西看的。

## 第三梯队：先补已交付的洞

这三个不是新功能，是「已经宣称有、实际走不通」的部分。排在业务能力之前，理由很直接：做完一个模块再回头改它的关键路径，比一开始就想清楚贵得多。

### 9. 新建用户的一次性密码

`UserService.create` 把密码设成 `Feat@<currentTimeMillis>` 入库，接口不返回明文。人被建出来就登不进去，管理员只能再点一次「重置密码」绕过去——而重置出来的是 `"Feat@" + id + "8X"`，知道 id 就能算出别人的临时密码。

正确流程：创建时生成随机初始密码 → 接口一次性返回 → `sys_user.must_change_password = 1` → 首次登录强制改密后清零。重置密码走同一条路径。

这是全项目唯一一条「功能在、主线不通」的路径，也是安全评审第一个会挑的地方。

### 10. 回收站

全表软删五字段、每条 SQL 带 `is_deleted = 0`，成本早就付了，但没有任何恢复入口：删错了只能改库。

- 用户 / 角色 / 部门各一个「已删除」视图 + 恢复接口
- 恢复前重新校验唯一性——用户名、角色编码可能已被新记录占用
- 关联关系一起恢复：`sys_user_role` 的软删行还在，`restoreUserRole` 的逻辑可直接复用
- 数据范围同样要生效，否则「仅本人」的账号能在回收站里看到全公司的已删数据

### 11. 审计日志的字段级差异

现在 `ActivityRecorder.record(kind, title, description, userId, operatorId)` 只存一句中文：「更新了用户 张三」「张三 的账号资料已变更 · 部门主管」。客户审计问的是「他把部门从技术中心改成了产品设计部」。

- 变更前后在 Service 里比对，只记真正变化的字段，格式 `字段: 旧值 → 新值`
- 密码这类字段只记「已重置」，不记值
- 前端详情抽屉展示 diff，列表仍显示摘要

## 第四梯队：每项目必重写的业务能力

排序依据换了：不看「RuoYi 有没有」，看「新项目第几天会撞上」。按真实交付的时间线走——第 2 天要传附件，第 3 天客户给一张 Excel，第 1 周状态字段开始变多，第 2 周要批量停用，第 2 个月才轮到参数配置。

这些功能的实现成本已经被 AI 抹平，真正要设计的是**「做成机制，还是散成常量」**。

### 12. 文件上传

`Storage` 接口 + 本地磁盘实现，OSS/MinIO 可插拔。要处理：大小限制、类型白名单、文件名随机化、按日期分目录、按业务归属（头像 / 附件 / 导入模板）。

### 13. Excel 导入导出

上一版路线图漏了这条，而它几乎是中国 ToB 交付的第一句话：「把这批数据导进去」「把列表导出来」。

- 导出：按当前筛选条件导出 xlsx。列定义与前端表格同源，不要两处维护
- 导入：模板下载 → 上传 → 校验（必填、格式、唯一性、外键存在）→ **逐行错误回写**，而不是整体失败
- 大文件走「先落盘再异步解析」，不要占着请求线程等 IO
- 不引 POI（体积大、JDK 8 下依赖重），用轻量实现或自带最小 xlsx 写出

### 14. 字典管理

`status` 是 `SMALLINT 0/1`，散在六张表和三个前端文件里，每加一个枚举都要改代码、重新构建。

`sys_dict_type` + `sys_dict_data`，前端 `useDict('user_status')` 取选项。

> 价值点不是「少写代码」，是**消除散落**——散落的枚举是 AI 最容易改错一处的那种东西。这也是它排在这里而不是更靠后的原因：它的收益在项目第二个月才显现，但迟到成本很高，散落得越久统一时改得越多。

### 15. 批量操作

列表页 90% 会被要求「批量停用 / 批量删除」，后端现在一个 batch 接口都没有。

- 批量接口必须按 id 逐个过 `canReach`，不能只校验第一个
- 返回**成功/失败清单**，部分成功要能说清哪几条失败、为什么；不要一个失败全回滚

### 16. 参数配置

`sys_config`，替代写死在代码和配置里的常量。与字典的区别：字典是「枚举选项」，参数是「单个值」（分页上限、密码长度、令牌有效期）。

> 注意：`@Value` 在 Feat 里靠 setter 注入，参数表要生效需要一个「读库覆盖」的初始化时机，别做成每次请求查库。

## 第五梯队：安全合规与运维闭环

不做也能跑，做了才敢过评审。这一层不产生新功能，只决定项目能不能验收。

### 17. 登录日志明细

现在只有 `sys_login_stat` 按天聚合，查不到「谁、从哪个 IP、什么时候、失败原因」。

`sys_login_log`：username、ip、user-agent、成功/失败原因、时间。与操作日志分开——操作日志记「改了什么」，登录日志记「谁进来了」。

### 18. 登录安全

- 连续失败 N 次锁定（存独立计数表，别在 `sys_user` 上加列——锁定时改的是别人的账号，会污染 `editor`）
- 在线会话列表 + 强制下线（`TokenStore` 已有 `removeOthers`，缺「列出全部会话」）
- 密码策略：长度、复杂度、有效期
- 会话持久化作为**可选**实现（Redis），默认保持单机零依赖。但企业要水平扩容就必须有，默认实现解决不了多实例

### 19. 定时任务

单机 cron 优先。**明确不做分布式调度中心**——xxl-job 已经占据这个位置。

### 20. 通知渠道，或者承认它是演示

`ActivityRecorder.record` 同时写 `sys_activity` 和 `sys_notification`，两个表职责重叠；通知只发给「被操作的人」，也就是「你被管理员改了资料」，价值很薄。

两条路选一条，不要悬着：

- 补渠道（邮件 / 短信 / 企业微信机器人），让它成为真正的通知中心；
- 或者明确它是演示模块，**不再往上加功能**——企业真正的通知需求是「告警发到群里」，那是 webhook，不是站内信。

### 21. `/metrics`

不是做监控面板。是把指标按 Prometheus 格式吐出去，交给 Grafana。

> 这条有前车之鉴：本项目曾尝试做「性能守门员」类运维产品，方向不成立——造面板是重复劳动，用户已有 SkyWalking / Prometheus / Grafana。让 Feat 被现有生态观测，才是正解。

## 非目标

写下来是为了避免反复讨论。

| 不做 | 理由 |
|---|---|
| **CRUD 代码生成器** | 它省的成本已被 AI 抹平；而生成物一旦被改就回不去，项目里长期并存两套范式，正是 AI 编程最贵的债务。见「2026 年的重估」 |
| 动态路由 | Feat 的路由在编译期确定。做成动态的等于放弃 AOT 的全部优势 |
| 表单构建器 / 低代码 | 同上，属于运行期元数据驱动的产物。企业要的是少写样板，不是不写代码 |
| 服务监控 / 缓存监控面板 | 已有成熟工具，自造面板是重复劳动 |
| 多租户 | 会让每一层都多一个 `tenant_id` 条件，与「轻量」定位冲突；真有需求应该做成独立分支 |
| 分布式调度中心 | xxl-job 已占据 |
| 岗位管理 | 与角色概念重叠，中小后台几乎不用 |

## 每个能力的「完成」定义

不是写完接口就算完成，以下五条缺一不可：

1. 有权限点，且后端每个接口独立校验（前端隐藏不算）；也要检查**旁路接口**——列表过滤只挡住「翻找」，日志、下拉、统计这些同样会暴露数据的出口要一并接上
2. 表上有软删除五字段，查询带 `is_deleted = 0`，且被删的每一行都能从回收站恢复——只置位不给恢复入口，等于花了软删的钱买了硬删的效果
3. 有对应的回归断言（不是手工点一遍）
4. README 的接口表同步更新
5. **横切能力不可绕过**：鉴权、数据范围、软删过滤、审计记录，漏接必须让编译失败或启动失败，不能靠「记得调一下」

## 顺序理由

一条主线：**先把「写错会炸」的部分变成机制，再补「已经宣称有但走不通」的部分，最后才加新功能。**

事务排第一，因为它是所有多语句写的正确性前提，也是判据 2 最直接的违反——现在的代码是「看起来对、跑起来脏」，这种 bug 没有报错，只有后果。

数据权限机制化排第二，因为它是判据 1 的样板：已经出过一次静默失效，而 AI 写新模块时百分之百会再犯一次。

迁移排第三，因为它决定 feat-plus 能不能进存量系统，而不只是新项目。

OpenAPI 从第三梯队提到第二梯队，不是因为它能生成代码，而是因为它是 AI 在这套代码里工作时的接口上下文——**契约要机器可读，实现不该被生成**。

补洞排在加功能之前，因为「新建用户登不进去」「删了恢复不了」这类问题，是已经做完的模块上的裂缝。新功能每加一个，踩到裂缝的面就大一点；而这几条修起来只要一两天。

业务能力的顺序不按重要性排，按**新项目撞上它的时间**排：文件上传（第 2 天）→ Excel 导入导出（第 3 天）→ 字典（第 1 周）→ 批量操作（第 2 周）→ 参数配置（第 2 个月）。字典排在这里合理，但它是这几项里唯一「迟到成本会累积」的——散落的枚举每多一天，统一时就要多改一处。

安全合规整层放在最后，不是因为不重要，而是它不产生功能、只决定能否验收。真到了要投标、要过等保的时候，这一层会整体前移到第一优先级——那是项目节奏决定的，不是设计决定的。
